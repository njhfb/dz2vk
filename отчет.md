# Отчёт по практической №2

---

## 1. Вариант и задача

| Поле | Значение |
|---|---|
| ФИО | Тимин Артём Витальевич |
| Тема | 1 CDC→SCD→Lakehouse |
| Состав решения | PostgreSQL → Debezium → Kafka → Spark Structured Streaming → Apache Iceberg на MinIO (каталог Iceberg REST), запросы через Trino |
| Данные, объем | таблица `accounts` (id, owner, status, updated_at). Для проверки 3 стартовые записи и несколько изменений руками (UPDATE, INSERT, DELETE), это учебный объём |

**Задача.** Есть операционная PostgreSQL, где записи постоянно меняются: у счёта меняется владелец, у заказа статус. Бухгалтерии и аналитикам нужна история на дату, например «кто был владельцем счёта на 1 марта». Ходить в источник тяжёлыми SELECT-ами нельзя, поэтому изменения забираем через CDC и складываем историю в Lakehouse в виде SCD-таблицы.

---

## 2. Источники и способы сбора

| Источник | Тип (поток / batch / CDC / документы в md pdf или другой / API) | Способ сбора |
|---|---|---|
| PostgreSQL, таблица `public.accounts` | CDC | Debezium читает WAL по логической репликации (`wal_level=logical`, плагин `pgoutput`). В таблицу SELECT-ы не ходят, поэтому источник не нагружается |
| Топик Kafka `pg.public.accounts` | поток | Сюда Debezium кладёт события изменений в JSON (поля `before`, `after`, `op`, `ts_ms`). Kafka нужна как буфер, чтобы события не терялись, если обработчик упал или отстал. Spark читает этот топик микробатчами |

Почему именно так: если бы я делал batch (раз в час выгружать всю таблицу), то пропустил бы промежуточные изменения. Например, владелец сменился два раза между выгрузками, и в истории осталась бы только последняя версия. CDC ловит каждое изменение.

Что есть на схеме:

## 4. Docker - что поднялось

Блок на схеме это что-то из процесса, описанного ниже в коде. Ниже все блоки со схемы и их статус.

| Блок | Статус (реализовано / нет) |
|---|---|
| PostgreSQL (wal_level=logical, таблица accounts из `init.sql`) | реализовано |
| Debezium (Kafka Connect), коннектор из `register-postgres.json` | реализовано |
| Apache Kafka (KRaft) | реализовано |
| MinIO + бакет `warehouse` | реализовано |
| Iceberg REST catalog | реализовано |
| Spark Structured Streaming (`spark_scd2.py`) | реализовано |
| Trino | реализовано |

Как запускал:

```bash
# 1. поднимаем всё
docker compose up -d
docker compose ps

# 2. регистрируем коннектор Debezium
curl -X POST -H "Content-Type: application/json" \
     --data @register-postgres.json http://localhost:8083/connectors
curl http://localhost:8083/connectors/inventory-connector/status

# 3. проверяем что события пошли в Kafka (снапшот трёх строк)
docker exec -it kafka_broker /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic pg.public.accounts --from-beginning --max-messages 3

# 4. смотрим логи Spark (после появления топика job сам стартует)
docker logs -f spark_scd2

# 5. вносим изменения в источник
docker exec -i postgres_source psql -U postgres -d inventory < demo-changes.sql

# 6. проверяем историю через Trino
docker exec -it trino_query trino --catalog lake --schema inventory \
  --execute "SELECT * FROM accounts_scd2 ORDER BY id, valid_from"
```

Известные ограничения моего решения:

- каталог Iceberg хранит список таблиц в памяти контейнера `iceberg-rest`. Если перезапустить только его, данные в MinIO останутся, но таблица пропадёт из каталога. Для чистого прогона я делаю `docker compose down -v`;
- если Spark упадёт между записью в Iceberg и сохранением checkpoint, батч обработается второй раз и в истории появятся лишние версии. Для учебной задачи оставил как есть;
- события, которые приходят позже новых версий (out-of-order между батчами), не обрабатываются. Для этого нужны watermark и более сложный MERGE.

## 5. Описание

По шагам что происходит с данными от источника до результата.

| Шаг | Для чего | Результат |
|---|---|---|
| 1. Изменение в PostgreSQL (INSERT / UPDATE / DELETE в `accounts`) | это сами данные, которые нужно сохранить с историей | запись попадает в WAL |
| 2. Debezium читает WAL | поймать каждое изменение без SELECT-ов в источник. Для UPDATE нужен `REPLICA IDENTITY FULL`, иначе в `before` не будет старых значений | JSON-событие с `before`, `after`, `op`, `ts_ms` |
| 3. Kafka, топик `pg.public.accounts` | буфер между источником и обработкой, события хранятся по порядку и не теряются | события лежат в топике и ждут потребителя |
| 4. Spark Structured Streaming, микробатч раз в 10 секунд | прочитать пачку событий и подготовить: убрать дубли (одинаковые `id`, `ts_ms`, `lsn`, `op`), упорядочить события по каждой записи | набор версий для вставки и набор строк для закрытия старых версий |
| 5. SCD Type 2 через `MERGE INTO` | если запись изменилась, закрыть текущую версию (`valid_to`, `is_current = false`) и вставить новую (`valid_from`, `is_current = true`). Для `op = d` только закрыть текущую версию | в таблице `accounts_scd2` хранится вся история |
| 6. Iceberg на MinIO, каталог REST | хранить историю дёшево в S3, а каталог знает какие таблицы есть и где их метаданные | файлы Parquet и metadata в бакете `warehouse` |
| 7. Trino | отвечать на SQL-запросы по дате | аналитик пишет условие `valid_from <= дата AND (valid_to IS NULL OR valid_to > дата)` и получает владельца на нужную дату |

Почему такие решения:

- **SCD Type 2.** Нужна именно история на дату, поэтому Type 1 (просто перезаписать) не подходит, старое значение пропадёт. Type 3 хранит только одно предыдущее значение (колонка `prev_owner`), а владелец может смениться много раз. Type 6 это смесь типов 1, 2 и 3, для моей задачи лишнее, поэтому я взял чистый Type 2 с флагом `is_current`.
- **Микробатч вместо непрерывного streaming.** Бухгалтерии не нужна задержка в миллисекунды, достаточно секунд или минуты. Запись в Iceberg пачками создаёт меньше мелких файлов, и `MERGE` проще делать в `foreachBatch`.
- **Время версии.** `valid_from` берётся из `ts_ms` события (время изменения в источнике), а не из времени обработки в Spark. Тогда история правильная, даже если обработка отстала. Это связь с темой про event-time.
- **Lakehouse (Iceberg + MinIO).** Хранение дешёвое, а Iceberg даёт `MERGE` и транзакции на S3, чего на голых parquet-файлах нет.

## 6. Выводы

Кратко, обратная связь.

В работе я собрал цепочку для варианта 1: PostgreSQL → Debezium → Kafka → Spark Structured Streaming → Iceberg на MinIO, а запросы к истории идут через Trino. Все блоки со схемы есть в `docker-compose.yml`, а логика SCD Type 2 написана в `spark_scd2.py`.

Главное, что я понял про CDC: он ловит каждое изменение прямо из WAL, поэтому источник не нагружается SELECT-ами и в истории не теряются промежуточные состояния, как при выгрузках раз в час. Для этого в PostgreSQL нужны `wal_level=logical` и `REPLICA IDENTITY FULL`, иначе в событии `UPDATE` не будет старых значений.

По SCD я выбрал Type 2, потому что нужен ответ на вопрос «кто был владельцем на дату». Type 1 перезаписывает старое значение, Type 3 помнит только одно предыдущее, а Type 6 для этой задачи избыточен. Самая интересная часть была в `MERGE INTO`: одним запросом закрывается старая версия (`valid_to`, `is_current = false`) и вставляется новая. Время версии я брал из `ts_ms` события, а не из времени работы Spark, чтобы история не зависела от задержек обработки.

Микробатчи Spark я выбрал вместо непрерывного streaming, потому что бухгалтерии не нужна задержка в миллисекунды, а запись пачками в Iceberg даёт меньше мелких файлов.

Что можно улучшить: хранить метаданные каталога Iceberg в PostgreSQL, а не в памяти контейнера, сделать запись в таблицу идемпотентной при повторной обработке батча и добавить watermark для событий, которые приходят с опозданием.
